# Feature Specification: Knowledge Representation

**Feature Branch**: `008-knowledge-representation`

**Created**: 2026-07-13

**Status**: Draft

**Input**: User description: "Design the Knowledge Representation stage for AlgoRAG from first
principles. Knowledge Representation must define how semantic knowledge is represented
independently of retrieval, indexing, graph storage, or any specific extraction technology.
The input is a validated ChunkSet produced by the Intelligent Chunking Engine (Spec 007).
The output is a canonical Knowledge Package. Introduce Knowledge Unit as the primary
architectural concept. Knowledge Graph must NOT be the primary output — it is one optional
downstream representation."

## Executive Summary

The pipeline SHALL gain a new **Knowledge Representation** stage that transforms a validated
**ChunkSet** (produced by `007-intelligent-chunking-engine`) into a canonical **Knowledge
Package** — a structured, fully-traceable collection of **Knowledge Units** and their
**Knowledge Relationships**, which becomes the foundation for downstream indexing, retrieval,
reasoning, planning, and answer generation.

Where today the pipeline treats chunks as the terminal semantic unit delivered directly to
indexing and retrieval, Knowledge Representation introduces an explicit semantic layer between
chunking and consumption: chunks remain immutable evidence; Knowledge Units become the
smallest independent semantic representations built from one or more chunks, each preserving
traceability — through a **collection of EvidenceReferences** — to every source chunk,
structural element, canonical document model, and original document. Knowledge Units are
**immutable once published**: any semantic modification produces a new Knowledge Unit rather
than mutating an existing one. Knowledge Relationships share this guarantee. The assembled
**Knowledge Package is likewise immutable**: any modification to its contained Knowledge
Units or Knowledge Relationships produces a new Knowledge Package. These immutability
guarantees apply end-to-end and directly support versioning, auditing, reproducibility,
incremental indexing, and deterministic processing.

The central architectural choice of this stage is that **not every piece of knowledge is an
entity**. The canonical unit of representation is a **Knowledge Unit** — a generic, typed
semantic fact that can express: a factual assertion, a procedure, a rule, a definition, a
measurement, a list, a table, a structured observation, or any other independently meaningful
semantic form. Knowledge Units reference their source evidence rather than replacing it.
**Named Entity Recognition (NER) is one optional, pluggable extraction strategy** — not a
prerequisite, not an assumption, and not the default.

The stage is **strategy-based** across four pluggable components: Knowledge Unit Extraction,
Knowledge Normalization (which resolves aliases, synonyms, and canonical identities before
relationships are discovered), Relationship Discovery (which itself runs a two-step
Candidate-then-Validation sub-pipeline), and Representation Strategy application. The
resulting Knowledge Package is representation-agnostic: it can produce a **Knowledge Graph**,
a Property Graph, a Semantic Network, a Hypergraph, or a Relational Representation — all as
optional downstream artifacts generated by pluggable Representation Strategies — without
changing the Knowledge Unit model. This preserves the generic-core-plus-YAML-packs
architecture established by `006` and `007` and ensures the stage remains independent of
embeddings, vector databases, retrieval engines, graph databases, rerankers, and answer
generation.

### Architectural Verdict

| Approach | Verdict |
| -------- | ------- |
| **Knowledge Unit–first: typed semantic units + evidence reference collections + knowledge normalization + relationship discovery sub-pipeline + pluggable representation strategies** | Preferred — generic, domain-agnostic, representation-independent, immutable units, traceable, and consistent with the platform's plug-and-play architecture. |
| **NER/Entity-first: knowledge graph as primary output, entities and spans as core model** | Rejected — assumes every fact is an entity; cannot represent procedures, rules, measurements, or definitions; tightly couples to graph storage and NER extraction; violates the generic-core constraint. |
| **Raw chunk pass-through: treat chunks as the final semantic unit** | Superseded — chunks are evidence, not semantic representations; this approach conflates evidence with knowledge and prevents structured reasoning, citation linking, and representation-strategy swapping. |
| **Single fixed representation (e.g., RDF triples only)** | Rejected — incompatible with the breadth of knowledge forms that must be supported; locks the architecture to one representation before downstream needs are known. |
| **Embedding-driven semantic clustering as knowledge extraction** | Rejected for this stage — violates the independence requirement; embeddings and vector similarity are downstream concerns, not a Knowledge Representation mechanism. |

## Architectural Principles

The following principles govern every design decision in this specification and every future
extension of this stage. They are non-negotiable and take precedence over implementation
convenience.

1. **Knowledge is represented independently of text.** Text is the medium through which
   knowledge is expressed; it is not knowledge itself. The Knowledge Representation stage
   exists to lift semantic meaning out of text and into explicitly typed, structured,
   independently queryable Knowledge Units.

2. **Text is evidence.** Chunks produced by the Intelligent Chunking Engine (`007`) are the
   immutable evidential record. They are referenced by Knowledge Units; they are never
   replaced, re-structured, or modified by any stage in this pipeline.

3. **Evidence is immutable.** Once a Chunk exists in the ChunkSet, it MUST NOT be modified,
   annotated, or discarded by the Knowledge Representation stage. EvidenceReferences point
   to Chunks; they never supersede them.

4. **Knowledge Units are immutable.** Once a Knowledge Unit is published into a Knowledge
   Package, it MUST NOT be mutated. Any semantic change produces a new Knowledge Unit with a
   new identity. This guarantees reproducibility, auditability, and deterministic incremental
   indexing.

5. **Knowledge Relationships are first-class entities.** A relationship between two Knowledge
   Units is not an edge label or an implicit graph property. It is an explicitly typed,
   independently traceable entity with its own identity, evidence references, and lifecycle.
   Relationships are immutable after publication for the same reasons Knowledge Units are.

6. **Representations are projections, not canonical knowledge.** A Knowledge Graph, a
   Property Graph, a Relational table, or any other derived format is a read-only view over
   a Knowledge Package. It does not replace, extend, or redefine the Knowledge Package.
   Canonical knowledge lives in Knowledge Units and Knowledge Relationships; representations
   are ephemeral artifacts derived from them.

7. **Extraction is strategy-based.** Every component that produces or transforms knowledge
   objects — extraction, normalization, relationship discovery — MUST be swappable behind a
   stable interface. No extraction technique, including NER, is hardwired into the pipeline
   core.

8. **Normalization precedes relationship discovery.** Semantic canonicalization — alias
   resolution, synonym normalization, duplicate detection — MUST complete for the document
   before any relationship candidates are generated. Relationships discovered over
   non-canonical representations are unreliable and must not enter the canonical model.

9. **Every semantic object must remain fully traceable.** Every Knowledge Unit and every
   Knowledge Relationship carries a non-empty collection of EvidenceReferences forming a
   complete, unbroken chain to the source Chunk, Structural Element, Canonical Document
   Model, and original document. No knowledge claim without evidence is permitted.

10. **Downstream consumers never redefine canonical knowledge.** No system downstream of
    this stage — retrieval, indexing, reasoning, answer generation, or representation
    strategy application — is permitted to modify Knowledge Units, Knowledge Relationships,
    EvidenceReferences, or the Knowledge Package. They are read-only consumers of canonical
    knowledge.

## Architecture: Knowledge Representation Pipeline

Every Knowledge Unit — its extraction, normalization, relationship discovery, and packaging —
flows through one explicit pipeline. Each stage has exactly one responsibility, and no stage
performs another stage's job:

```
Validated ChunkSet
        ↓
Knowledge Unit Extraction
        ↓
Raw Knowledge Units
        ↓
Knowledge Normalization
        ↓
Normalized Knowledge Units
        ↓
Relationship Discovery
        ↓
Knowledge Relationships
        ↓
Knowledge Package Assembly
        ↓
Knowledge Validation
        ↓
Knowledge Validation Report
        ↓
Knowledge Package
```

- **Validated ChunkSet** — the terminal output of `007-intelligent-chunking-engine`: an
  ordered, validated collection of Chunks for one document. Each Chunk carries a stable
  identity, lineage, parent/child and previous/next relationships, and inherited provenance
  from the Canonical Document Model (`006-document-intelligence-pipeline`). This is the sole
  input to the Knowledge Representation stage; the stage never re-parses raw documents or
  re-runs chunking.

- **Knowledge Unit Extraction** — a swappable, strategy-based component that reads the
  ChunkSet and produces raw Knowledge Units. Extractor strategies may use any approach:
  rule-based pattern matching, structural analysis, NER (as one optional strategy),
  procedural text parsing, table decomposition, mathematical expression parsing, or any
  future technique. All extractor strategies share one stable interface and contribute to the
  same Knowledge Unit model regardless of their internal technique. No extractor strategy
  embeds, retrieves, or calls an LLM by default unless explicitly configured as an optional
  alternative behind the same interface.

- **Raw Knowledge Units** — the extraction output: a collection of typed, independently
  meaningful semantic representations, each referencing a non-empty collection of
  EvidenceReferences (never a single scalar reference, since knowledge often originates from
  multiple chunks or structural elements). A Knowledge Unit is not constrained to RDF triple
  form; it is the smallest unit that: (a) preserves meaning independently, (b) can be cited,
  (c) can participate in relationships, (d) can be indexed independently, and (e) is
  traceable to its source evidence. Once published into the Knowledge Package, every
  Knowledge Unit is **immutable**: any semantic modification creates a new Knowledge Unit
  rather than mutating an existing one.

- **Knowledge Normalization** — a swappable, strategy-based stage that receives Raw
  Knowledge Units and produces Normalized Knowledge Units by establishing canonical semantic
  identities before Relationship Discovery runs. Normalization responsibilities are limited
  to: alias resolution, synonym normalization, canonical naming, structural normalization,
  and duplicate semantic detection. Knowledge Normalization is a pure canonicalization stage:
  it MUST NOT introduce new semantic meaning; it MUST NOT infer new knowledge claims; it
  MUST NOT create new Knowledge Units beyond those derived from merging detected duplicates;
  it MUST NOT create relationships between Knowledge Units; it MUST NOT modify any
  EvidenceReference collection or any source evidence. Because Normalized Knowledge Units
  feed Relationship Discovery, normalization MUST complete for the entire document before any
  relationship candidates are generated. Normalization is pluggable: the default strategy is
  deterministic and rule-based; alternative strategies (e.g., embedding-assisted
  deduplication) may be configured optionally behind the same interface.

- **Normalized Knowledge Units** — the normalization output: the same set of Knowledge Units
  with resolved canonical identities, deduplicated where semantically equivalent units were
  detected, and with surface-form variations collapsed. Each normalized unit retains its
  original EvidenceReference collection intact; normalization never discards evidence.

- **Relationship Discovery** — a component that analyzes Normalized Knowledge Units and
  identifies semantic relationships between them. Relationship Discovery is itself an explicit
  sub-pipeline:

  ```
  Normalized Knowledge Units
          ↓
  Relationship Candidate Discovery
          ↓
  Relationship Validation
          ↓
  Knowledge Relationships
  ```

  - **Relationship Candidate Discovery** — generates candidate semantic relationships between
    Knowledge Units: dependency, equivalence, contradiction, elaboration, containment,
    sequence, derivation, or any other type supported by the active strategy. Each candidate
    carries a relationship type, a source unit id, a target unit id, and its own
    EvidenceReference collection. Candidate discovery is strategy-based and swappable.
  - **Relationship Validation** — filters or flags relationship candidates that reference
    non-existent unit ids, produce cycles where not permitted by type, or violate configured
    quality constraints. Relationship Validation MUST NOT modify Knowledge Units.
  - **Knowledge Relationships** — the validated set of typed relationship edges between
    Knowledge Units that survives both candidate generation and validation.

  Relationship Discovery never modifies Knowledge Units at any sub-stage; it produces
  Knowledge Relationships as its sole output.

- **Knowledge Package Assembly** — collects Normalized Knowledge Units, Knowledge
  Relationships, and their shared Evidence Registry into a single, self-contained,
  serializable entity for one document. It does not interpret or modify Knowledge Units or
  Relationships; it consolidates them into a structured package and attaches statistics
  (unit counts by type, relationship counts by type, coverage metrics) and metadata
  (originating ChunkSet identity, applied strategy identifiers).

- **Knowledge Validation** — validates the assembled Knowledge Package against defined
  quality rules: completeness of every unit's EvidenceReference collection, absence of
  dangling unit references in relationships, Knowledge Unit type correctness, and full
  traceability chain integrity. It produces exactly one **Knowledge Validation Report** and
  never modifies Knowledge Units or Relationships.

- **Knowledge Validation Report** (`KnowledgeValidationReport`) — the formal, structured
  outcome of validation and an immutable audit artifact: overall `status`, named `errors`
  (blocking rule violations), `warnings` (non-blocking), `validation_results` (per-rule
  outcomes), `statistics`, and `metadata`. Retained independently of re-running the pipeline
  for observability and debugging.

- **Knowledge Package** — the stage's terminal output: a validated, self-contained
  collection of Normalized Knowledge Units and Knowledge Relationships for one document, with
  complete evidence traceability, ready to be consumed by any downstream Representation
  Strategy (Knowledge Graph, Property Graph, Semantic Network, Hypergraph, Relational, or
  others) without modification. Representation Strategies consume the Knowledge Package as a
  whole — not individual Knowledge Units in isolation.

### Evidence Model

Every Knowledge Unit and every Knowledge Relationship carries a complete chain of evidence
references tracing it to its sources:

```
EvidenceReference
        ↓
Chunk (from ChunkSet)
        ↓
Structural Element(s) (from DocumentModel)
        ↓
Canonical Document Model (006)
        ↓
Original Document / Asset
```

An `EvidenceReference` is a first-class entity that captures: the source Chunk id(s), the
source Structural Element id(s), the Document Model identity, and the asset/document identity.
Evidence is never inlined into Knowledge Units — it is referenced. Chunks remain immutable
evidence; Knowledge Units are semantic representations built on top of them.

### KnowledgeUnit Model

A `KnowledgeUnit` is a first-class architectural entity. The following conceptual fields
define the responsibilities every Knowledge Unit must expose, independent of any specific
implementation representation:

| Field | Responsibility |
| ----- | -------------- |
| `id` | Stable, deterministic identity derived from source evidence and extraction configuration |
| `type` | Semantic type from the supported vocabulary (`fact`, `procedure`, `rule`, `definition`, `measurement`, `list`, `table`, `assertion`, `structured_observation`, extensible) |
| `semantic_content` | The structured semantic representation of the unit's meaning — not constrained to RDF triple or entity-span form; may be a statement, ordered steps, key-value pairs, a table projection, or another structured form appropriate to the type |
| `participants` | Named roles or actors involved in the unit's semantic content where relevant (e.g., subject/object for a fact, agent/steps for a procedure); absent for types where no participants apply |
| `attributes` | Qualifiers, units of measure, temporal scope, confidence (when produced by a probabilistic strategy), or other type-specific descriptive properties of the unit's content |
| `evidence_references` | A non-empty **collection** of `EvidenceReference` entities tracing this unit to its source Chunk(s), Structural Element(s), Document Model, and original document; always a collection — never a single scalar reference — because knowledge may originate from multiple chunks or structural elements |
| `relationships` | The set of `KnowledgeRelationship` identifiers involving this unit (populated after Relationship Discovery; read-only on the unit itself) |
| `metadata` | Extraction strategy identifier, normalization status, creation timestamp, and any other non-semantic bookkeeping that does not alter the unit's meaning |

The exact internal representation of these fields is an implementation-phase decision. The
conceptual responsibilities above are fixed by this specification: any implementation of
`KnowledgeUnit` MUST expose all of them. Once a Knowledge Unit is published into a Knowledge
Package it is **immutable** — any semantic modification (to `type`, `semantic_content`,
`participants`, or `attributes`) MUST produce a new Knowledge Unit with a new identity
rather than mutating the existing one.

### KnowledgeRelationship Model

A `KnowledgeRelationship` is a first-class architectural entity — not an implicit graph edge
or a property of the units it connects. The following conceptual fields define the
responsibilities every Knowledge Relationship must expose, independent of any specific
implementation representation:

| Field | Responsibility |
| ----- | -------------- |
| `id` | Stable, deterministic identity derived from the source unit id, target unit id, relationship type, and the Relationship Discovery strategy and configuration in effect |
| `relationship_type` | The semantic type of the relationship, drawn from the supported vocabulary (`dependency`, `equivalence`, `contradiction`, `elaboration`, `containment`, `sequence`, `derivation`, extensible) |
| `source_unit` | The id of the Knowledge Unit that is the source or subject of the relationship |
| `target_unit` | The id of the Knowledge Unit that is the target or object of the relationship |
| `evidence_references` | A non-empty **collection** of `EvidenceReference` entities supporting the existence of this relationship — always a collection, never a single scalar; may include references from both source and target units, or from additional Chunks that explicitly state the relationship |
| `attributes` | Optional qualifiers on the relationship: directionality (directed or undirected), confidence qualifier (present only when produced by a probabilistic strategy), temporal scope, or other type-specific properties |
| `metadata` | Relationship Discovery strategy identifier, creation timestamp, and any non-semantic bookkeeping that does not alter the relationship's meaning |

The exact internal representation of these fields is an implementation-phase decision. The
conceptual responsibilities above are fixed by this specification: any implementation of
`KnowledgeRelationship` MUST expose all of them. Once a Knowledge Relationship is published
into a Knowledge Package it is **immutable** — any modification (to `relationship_type`,
`source_unit`, `target_unit`, or `attributes`) MUST produce a new Knowledge Relationship
with a new identity rather than mutating the existing one, for the same reasons Knowledge
Units are immutable.

### KnowledgeValidationReport Model

A `KnowledgeValidationReport` is a first-class architectural entity and an immutable audit
artifact. It is produced exactly once per pipeline run, before the Knowledge Package is
returned, and is retained independently for observability and debugging. The following
conceptual fields define its structure:

| Field | Responsibility |
| ----- | -------------- |
| `status` | Overall validation outcome: one of `passed`, `passed_with_warnings`, or `failed` |
| `errors` | The set of named, blocking rule violations found during validation — each error corresponds to a named quality rule (FR-024); an error causes `status` to be `failed` |
| `warnings` | The set of named, non-blocking observations — each warning is recorded without preventing the Knowledge Package from being returned; causes `status` to be `passed_with_warnings` when no errors exist |
| `validation_results` | Per-rule outcome records: one entry per quality rule checked, indicating pass, error, or warning, along with the specific Knowledge Unit ids or Knowledge Relationship ids implicated (if any) |
| `statistics` | Counts derived from the validation run: total units checked, total relationships checked, error count, warning count, and auto-correction count (if any auto-corrections were applied per documented rules) |
| `metadata` | Run identity: originating ChunkSet id, Knowledge Package id, validation timestamp, and the Knowledge Validation strategy or rule set version applied |

A `KnowledgeValidationReport` is **immutable once produced** — it is an audit artifact that
records the state of the Knowledge Package at the moment of validation. No pipeline stage,
downstream consumer, or Representation Strategy MUST modify or replace it after production.
Re-running the pipeline produces a new report; it does not overwrite the previous one.

### KnowledgePackage Model

A `KnowledgePackage` is a first-class architectural entity — the self-contained,
serializable, validated output for one document. The following conceptual fields define its
structure:

| Field | Responsibility |
| ----- | -------------- |
| `knowledge_units` | The complete, ordered collection of Normalized Knowledge Units for the document |
| `knowledge_relationships` | The complete collection of typed Knowledge Relationships between units — first-class entities with their own ids and evidence references |
| `evidence_registry` | The consolidated index of all `EvidenceReference` entities referenced by any unit or relationship in this package, keyed by reference id for efficient lookup without re-traversing individual units |
| `validation_report` | The `KnowledgeValidationReport` produced during Knowledge Validation — present in every package, including packages that passed with zero violations |
| `metadata` | Package-level identity: originating ChunkSet id, Document Model id, asset/document id, applied extraction strategy identifier, applied normalization strategy identifier, applied relationship discovery strategy identifier, and creation timestamp |
| `statistics` | Derived counts and coverage metrics: Knowledge Unit count by type, Knowledge Relationship count by type, EvidenceReference coverage percentage (fraction of input Chunks referenced by at least one unit), and validation rule pass/fail counts |

A **published KnowledgePackage is immutable**. Any modification to the contained Knowledge
Units or Knowledge Relationships MUST result in a new KnowledgePackage rather than mutating
the existing package. This guarantees deterministic processing, reproducibility, versioning,
and auditability across the entire pipeline.

Downstream Representation Strategies consume the `KnowledgePackage` as a whole — not
individual Knowledge Units in isolation — and MUST NOT modify any field of the package they
receive. They are read-only consumers of canonical knowledge.

### Representation Strategies (Optional Downstream)

A Knowledge Package is representation-agnostic. Any downstream consumer may apply a
**Knowledge Representation Strategy** to generate a specific representation format from the
same package. Representation Strategies are **pure read-only projections** of canonical
knowledge — they derive a new artifact from the Knowledge Package without redefining,
extending, or replacing it.

A Representation Strategy MUST:
- Consume the Knowledge Package as a whole input.
- Produce exactly one alternative representation format as its output.
- Treat all Knowledge Units, Knowledge Relationships, EvidenceReferences, and the Knowledge
  Package itself as read-only.

A Representation Strategy MUST NOT:
- Modify any Knowledge Unit, Knowledge Relationship, EvidenceReference, or Knowledge Package
  field.
- Create new Knowledge Units or Knowledge Relationships.
- Introduce new evidence or citations not present in the Knowledge Package.
- Persist, index, or embed the Knowledge Package or any of its contents (these are
  downstream concerns outside this stage).

| Representation | Description |
| -------------- | ----------- |
| Knowledge Graph | Directed labeled multigraph of Knowledge Units (nodes) and Relationships (edges) |
| Property Graph | Graph with rich property sets on nodes and edges |
| Semantic Network | Network of associative, typed links between concepts |
| Hypergraph | Graph with hyperedges connecting more than two Knowledge Units |
| Relational Representation | Tabular/relational projection of Knowledge Units and Relationships |

None of these representations are the core output of this stage. They are optional,
separately generated projection artifacts produced by pluggable strategies that consume an
immutable Knowledge Package. Additional representation formats may be added by implementing
the `KnowledgeRepresentationStrategy` interface without changing the Knowledge Unit model,
the Knowledge Relationship model, or the Knowledge Package structure. Vector representations
(embedding-ready serializations) are downstream indexing artifacts, not knowledge
representations, and are therefore out of scope for this stage and this strategy list.

### Component Responsibility Boundaries

| Component | Responsible for | Never does |
| --------- | --------------- | ---------- |
| Knowledge Unit Extraction | Producing raw Knowledge Units from ChunkSet | Normalizing units; discovering relationships; assembling the package |
| Knowledge Normalization | Resolving canonical identities, aliases, synonyms, and duplicates across raw Knowledge Units | Modifying EvidenceReferences or source evidence; extracting new units; discovering relationships |
| Relationship Discovery | Generating relationship candidates and validating them into Knowledge Relationships | Modifying Knowledge Units at any sub-stage; assembling the package |
| Knowledge Package Assembly | Consolidating Normalized Knowledge Units, Relationships, Evidence Registry, statistics, and metadata into one package | Interpreting or modifying semantic content; generating representations |
| Knowledge Validation | Validating the Knowledge Package; producing the Validation Report | Modifying Knowledge Units or Relationships; generating representations |
| Representation Strategy | Generating one specific representation format as a pure read-only projection of an immutable Knowledge Package | Extracting, normalizing, modifying, or creating Knowledge Units, Relationships, or EvidenceReferences |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Any semantic form becomes a citable, traceable Knowledge Unit (Priority: P1)

A platform operator ingests a document whose ChunkSet contains procedural instructions, a
definition, a data table, and a regulatory assertion. With Knowledge Representation, each of
these produces a Knowledge Unit of the appropriate type — not only entities — and every
Knowledge Unit can be cited back to the exact chunk, structural element, and original document
that produced it.

**Why this priority**: This is the entire premise of the feature — representing the full
breadth of semantic knowledge forms from a ChunkSet, not reducing everything to entities. It
also directly enables production-grade citations (Constitution VI.4) at the knowledge level.

**Independent Test**: Ingest a fixture ChunkSet containing at least one chunk of each of the
following semantic forms: a factual assertion, a step-by-step procedure, a domain definition,
a measurement, and a tabular data record. Verify each produces at least one Knowledge Unit of
the correct type, and that each Knowledge Unit's evidence reference resolves to its source
chunk and structural element.

**Acceptance Scenarios**:

1. **Given** a chunk containing a procedure (numbered steps), **When** Knowledge Unit
   Extraction runs, **Then** the resulting Knowledge Unit has type `procedure`, preserves the
   steps as structured content, and references the source chunk id in its EvidenceReference.
2. **Given** a chunk containing a measurement value with units, **When** Knowledge Unit
   Extraction runs, **Then** the resulting Knowledge Unit has type `measurement`, and following
   its EvidenceReference chain traces back to the specific structural element and original
   document.
3. **Given** a chunk containing a tabular record, **When** Knowledge Unit Extraction runs,
   **Then** the resulting Knowledge Unit has type `table` or an appropriate structured type,
   not a flattened string entity, and its evidence reference includes the source table-row
   structural element id.

### User Story 2 - Strategy-based pipeline with zero knowledge model change (Priority: P1)

A platform maintainer wants to add a new Knowledge Unit Extraction strategy, a new Knowledge
Normalization strategy, or a new Relationship Discovery strategy — for example, a mathematical
expression parser, an embedding-based deduplication normalizer, or a co-reference-based
relationship discoverer — without changing the Knowledge Package contract, the Knowledge Unit
model, or any downstream consumer.

**Why this priority**: Extensibility without core modification is the explicit architectural
mandate for this platform; without it, every new knowledge domain reintroduces core changes.

**Independent Test**: Register a second Knowledge Unit Extraction strategy and a second
Knowledge Normalization strategy. Switch a project's configuration to use them. Verify the
resulting Knowledge Package has the same structural shape (Normalized Knowledge Units with
EvidenceReference collections, Knowledge Relationships, Validation Report, statistics) and
that downstream consumers require zero code changes.

**Acceptance Scenarios**:

1. **Given** two Knowledge Unit Extraction strategies are registered, **When** a project's
   pack selects one via configuration, **Then** that strategy's extraction logic runs and the
   resulting Knowledge Package has the standard shape with no change to the pipeline's core
   dispatch logic or the Knowledge Normalization stage downstream.
2. **Given** a new Knowledge Normalization strategy is added and registered, **When** existing
   projects continue running their current normalization strategy, **Then** neither their
   behavior nor any downstream consumer code changes.
3. **Given** NER is configured as an optional extraction strategy for a specific project,
   **When** extraction runs, **Then** it produces Knowledge Units of entity-compatible types,
   but when NER is not configured, the stage still produces Knowledge Units via the default
   strategy without any NER-specific fallback logic in core. In both cases, Knowledge
   Normalization runs on the resulting units identically.

### User Story 3 - Complete evidence traceability for every Knowledge Unit (Priority: P1)

An answer generation system produces a response and must include a citation traceable all the
way from the Knowledge Unit that supported the answer back to the exact chunk, structural
element, canonical document model, and original document. This traceability chain MUST be
available on every Knowledge Unit without additional queries or re-processing.

**Why this priority**: Production-grade citation (Constitution VI.4) and audit requirements
demand that no knowledge claim be untraced; this is also a prerequisite for the future
reasoning and planning stages that will consume Knowledge Packages.

**Independent Test**: Produce a Knowledge Package for a fixture document. For every Knowledge
Unit in the package, traverse its entire `evidence_references` collection and confirm every
reference in it resolves to: a valid Chunk id (present in the originating ChunkSet), a valid
Structural Element id (present in the Canonical Document Model), the Document Model identity,
and the original asset identity.

**Acceptance Scenarios**:

1. **Given** any Knowledge Unit in a Knowledge Package, **When** its `evidence_references`
   collection is inspected, **Then** it is non-empty and every reference in it resolves to one
   or more valid Chunk ids from the originating ChunkSet.
2. **Given** any Knowledge Unit, **When** each EvidenceReference in its collection is
   traversed completely, **Then** each terminates at the original document/asset identity
   without any broken or missing links at any of the four traceability levels.
3. **Given** a Knowledge Relationship between two Knowledge Units, **When** the relationship's
   `evidence_references` collection is inspected, **Then** it is non-empty and resolves to at
   least one valid Chunk id per reference, even when the relationship was inferred rather than
   directly stated.
4. **Given** two semantically equivalent Knowledge Units merged by Knowledge Normalization
   into one canonical unit, **When** the merged unit's `evidence_references` collection is
   inspected, **Then** it contains the EvidenceReferences from both original units — none
   discarded.

### User Story 4 - Knowledge Normalization establishes canonical identities before relationship discovery (Priority: P2)

A platform engineer ingests a document where the same concept appears under multiple surface
forms — a medication referred to as both a generic name and a brand name in different chunks,
or a procedure that is abbreviated in one section and spelled out in another. With Knowledge
Normalization, these surface-form variations are resolved into a single canonical Knowledge
Unit before Relationship Discovery runs, so relationships are discovered between meaningful
concepts, not between fragmented surface representations.

**Why this priority**: Without normalization, Relationship Discovery would produce duplicated
or fragmented relationship graphs for the same underlying concepts. Normalization is a
prerequisite for high-quality relationship coverage.

**Independent Test**: Ingest a fixture ChunkSet containing the same concept under two
different surface forms. Verify that after Knowledge Normalization, exactly one canonical
Knowledge Unit exists for that concept, its `evidence_references` collection includes
references from both source chunks, and Relationship Discovery operates on the deduplicated
unit rather than on two separate units.

**Acceptance Scenarios**:

1. **Given** two raw Knowledge Units whose semantic content is identified as equivalent by
   the active normalization strategy, **When** Knowledge Normalization runs, **Then** exactly
   one canonical Knowledge Unit exits normalization; its `evidence_references` collection
   includes the references from both original units.
2. **Given** a Knowledge Unit whose surface-form name is an alias resolvable to a canonical
   form, **When** Knowledge Normalization runs, **Then** the canonical form is reflected in
   `semantic_content` and the original alias is preserved in `attributes` or `metadata`
   for auditability.
3. **Given** the normalization stage with the default deterministic strategy, **When** the
   same raw Knowledge Units are normalized twice with the same configuration, **Then** the
   output Normalized Knowledge Units are identical both times.

### User Story 5 - Knowledge Graph as one optional representation, not the core model (Priority: P3)

A graph visualization tool wants to render a document's knowledge as a directed labeled graph.
With Knowledge Representation, it can apply a Knowledge Graph Representation Strategy to a
Knowledge Package to generate this graph — without the Knowledge Unit model or pipeline
needing to know about or depend on graph storage, graph databases, or RDF.

**Why this priority**: This explicitly corrects the NER/KG-first framing the user identified
as incorrect in the draft; it validates that the architecture keeps the Knowledge Package
representation-agnostic and the Knowledge Graph as an optional artifact.

**Independent Test**: Generate a Knowledge Package for a fixture document. Apply a Knowledge
Graph Representation Strategy to it. Verify the resulting graph contains nodes derived from
Knowledge Units and edges derived from Knowledge Relationships, and that re-applying a
different representation strategy (e.g., a relational projection) to the same Knowledge
Package produces a different format without modifying the package.

**Acceptance Scenarios**:

1. **Given** a finalized Knowledge Package, **When** a Knowledge Graph Representation
   Strategy is applied, **Then** it produces a graph structure without modifying any Knowledge
   Unit or Knowledge Relationship in the package.
2. **Given** a finalized Knowledge Package, **When** two different Representation Strategies
   are applied sequentially, **Then** both produce their respective formats and neither
   modifies the package; the package remains identical before and after both applications.
3. **Given** a project that does not configure any Representation Strategy, **When** the
   Knowledge Representation stage runs, **Then** it still produces a valid, complete Knowledge
   Package and no graph structure is generated; the absence of a graph is not an error.

### User Story 6 - Knowledge validation gates malformed or untraceable units (Priority: P3)

Before a Knowledge Package reaches downstream consumers, the platform needs an automatic gate
that catches Knowledge Units missing evidence references, relationships referencing
non-existent units, or malformed unit content — and reports them explicitly without silently
passing them through.

**Why this priority**: A safety net making every other guarantee in this spec enforceable and
observable. The pipeline can function while other stories land first; hence P3.

**Independent Test**: Introduce intentionally malformed inputs: a Knowledge Unit with no
EvidenceReference, a Knowledge Relationship referencing a non-existent unit id, and a
Knowledge Unit of an unrecognized type. Verify each is caught and reflected in the Knowledge
Validation Report's `errors` or `warnings` without any violation silently reaching the
Knowledge Package.

**Acceptance Scenarios**:

1. **Given** a Knowledge Unit with no EvidenceReference, **When** Knowledge Validation runs,
   **Then** it is flagged or filtered with a named failed rule in the Validation Report; it
   does not reach the output Knowledge Package silently.
2. **Given** a Knowledge Relationship referencing a Knowledge Unit id not present in the
   current package, **When** Knowledge Validation runs, **Then** it is flagged as a dangling
   reference in the Validation Report.
3. **Given** a Knowledge Validation Report for any run, **When** it is inspected after the
   run, **Then** it is available in full (status, errors, warnings, validation_results,
   statistics, metadata) without re-running the pipeline.

### Edge Cases

- A ChunkSet consisting of a single degraded fallback chunk (per `006` degraded-extraction
  path) → Knowledge Unit Extraction still runs on that lone chunk; the resulting Knowledge
  Package may contain few or low-confidence units, but extraction does not crash and the
  package is valid.
- A chunk whose semantic content does not clearly map to any known Knowledge Unit type →
  falls back to a `fact` or `assertion` type with the chunk's content preserved; no content
  is silently dropped.
- A Knowledge Relationship whose source and target Knowledge Units are produced by different
  extraction strategies → valid as long as both units exist in the Knowledge Package; the
  pipeline does not enforce strategy homogeneity within a package.
- Re-processing the same unchanged ChunkSet with the same extraction, normalization, and
  relationship discovery strategies and configuration → produces a Knowledge Package with
  identical Knowledge Unit ids, types, evidence references, and relationships (idempotent
  and reproducible).
- A ChunkSet for a document with no structured content (plain unstructured prose only) →
  Knowledge Unit Extraction produces `assertion` or `fact` units from prose chunks; no
  special case for "unstructured" mode; all paths through the pipeline produce a valid
  Knowledge Package.
- A Knowledge Unit whose source chunk was itself derived from a merged group of structural
  elements → its `evidence_references` collection carries all contributing Chunk ids and all
  contributing Structural Element ids across its references, not just the first.
- Knowledge Normalization identifies two raw Knowledge Units as duplicates but their
  `evidence_references` collections reference different Chunks → the merged canonical unit's
  `evidence_references` collection includes all distinct references from both; no evidence
  is discarded.
- A Relationship Discovery strategy that produces zero relationships for a document →
  valid; the Knowledge Package carries an empty relationship set and still passes validation;
  zero relationships is not a validation error.
- An extraction strategy that produces more Knowledge Units than a configured maximum →
  the Knowledge Validation stage flags the excess as a warning; the package is not silently
  truncated without recording the truncation.

## Requirements *(mandatory)*

### Functional Requirements

#### Input Contract & Independence

- **FR-001**: The Knowledge Representation stage MUST consume only the validated ChunkSet
  produced by `007-intelligent-chunking-engine` as its input; it MUST NOT re-parse raw
  documents, re-run chunking, or access any storage layer (vector store, graph database,
  relational database) directly.
- **FR-002**: The stage's core logic MUST NOT contain any domain-name-specific conditionals
  (no `if domain == "pharmacy"` or equivalent); all domain-specific extraction behavior MUST
  be expressed as declarative configuration (strategy selection and parameters) consumed by
  generic code, following the existing YAML pack precedence (generic < domain < project).
- **FR-003**: The stage MUST remain fully independent of: embedding generation, vector
  databases, retrieval engines, reranking, query understanding, answer generation, and graph
  databases. None of these systems MUST be invoked or depended upon by the stage's core
  pipeline.

#### Knowledge Unit Model

- **FR-004**: The Knowledge Unit MUST be the primary architectural entity of this stage. A
  Knowledge Unit MUST represent the smallest independently meaningful semantic fact that:
  (a) preserves meaning on its own, (b) can be cited with a complete evidence reference,
  (c) can participate in relationships with other Knowledge Units, (d) can be indexed
  independently, and (e) is traceable to its source evidence.
- **FR-005**: The Knowledge Unit model MUST support, at minimum, the following semantic
  types without requiring different extraction pipelines or different evidence models for each:
  `fact`, `procedure`, `rule`, `definition`, `measurement`, `list`, `table`,
  `assertion`, `structured_observation`. Additional types MAY be introduced as additive
  vocabulary extensions without changing the Knowledge Unit model shape.
- **FR-006**: A Knowledge Unit MUST NOT be constrained to RDF triple form or any other
  specific graph serialization. Its content representation MUST be generic enough to hold
  structured content of any supported semantic type (FR-005).
- **FR-007**: Every Knowledge Unit MUST expose the following conceptual responsibilities
  (per the KnowledgeUnit Model): a stable deterministic `id` (FR-008); a `type` from the
  supported vocabulary (FR-005); a `semantic_content` field holding the structured semantic
  representation; a `participants` field for named roles where applicable; an `attributes`
  field for qualifiers and type-specific properties; an `evidence_references` field holding a
  non-empty **collection** of EvidenceReferences (FR-013–FR-016); a `relationships` field
  listing relationship ids (populated after Relationship Discovery, read-only on the unit);
  and a `metadata` field carrying non-semantic bookkeeping. Every implementation of
  KnowledgeUnit MUST expose all of these responsibilities.
- **FR-008**: Knowledge Unit identity MUST be stable and deterministic: re-running the same
  extraction strategy on the same unchanged ChunkSet with the same configuration MUST always
  produce the same Knowledge Unit ids.
- **FR-008a**: Every Knowledge Unit MUST be **immutable once published** into a Knowledge
  Package. Any semantic modification to `type`, `semantic_content`, `participants`, or
  `attributes` MUST produce a new Knowledge Unit with a new identity rather than mutating
  the existing unit. This immutability guarantees reproducibility, auditability, and
  deterministic incremental indexing.

#### Knowledge Relationship Model

- **FR-009**: Knowledge Relationships MUST be first-class entities, not implicit graph edges.
  Each Knowledge Relationship MUST expose the following conceptual responsibilities (per the
  KnowledgeRelationship Model): a stable deterministic `id`; a `relationship_type` from the
  supported vocabulary (FR-010); a `source_unit` id; a `target_unit` id; an
  `evidence_references` field holding a non-empty **collection** of EvidenceReferences (never
  a single scalar reference); an `attributes` field for directionality, confidence qualifier,
  and other type-specific properties; and a `metadata` field. Every implementation of
  KnowledgeRelationship MUST expose all of these responsibilities.
- **FR-009a**: Every Knowledge Relationship MUST be **immutable once published** into a
  Knowledge Package. Any modification to `relationship_type`, `source_unit`, `target_unit`,
  or `attributes` MUST produce a new Knowledge Relationship with a new identity, for the
  same reasons as Knowledge Unit immutability (FR-008a).
- **FR-010**: The relationship type vocabulary MUST include, at minimum: `dependency`,
  `equivalence`, `contradiction`, `elaboration`, `containment`, `sequence`, `derivation`.
  Additional types MAY be introduced as additive vocabulary extensions.
- **FR-011**: Every Knowledge Relationship MUST reference only Knowledge Unit ids present in
  the same Knowledge Package; dangling references MUST be caught by Knowledge Validation
  (FR-024) and MUST NOT appear in the final output package.
- **FR-012**: A Knowledge Relationship MAY carry an optional confidence qualifier when
  produced by a probabilistic Relationship Discovery strategy. When produced by a
  deterministic strategy, no confidence qualifier is present or required.

#### Evidence Model

- **FR-013**: Every Knowledge Unit and every Knowledge Relationship MUST maintain a complete,
  unbroken evidence traceability chain via a **non-empty collection** of `EvidenceReference`
  entities. No Knowledge Unit or Relationship is permitted in a Knowledge Package without at
  least one EvidenceReference. EvidenceReferences are always a collection — never a single
  scalar — because knowledge may originate from multiple chunks or structural elements.
- **FR-014**: Each `EvidenceReference` in a collection MUST carry, at minimum: one or more
  source Chunk ids (from the input ChunkSet), one or more source Structural Element ids
  (from the Canonical Document Model), the Document Model identity, and the asset/document
  identity. All four levels of the traceability chain MUST be present in every individual
  EvidenceReference; partial references are not valid.
- **FR-015**: All Chunk ids and Structural Element ids named in EvidenceReferences MUST
  correspond to entities present in the originating ChunkSet and Canonical Document Model
  respectively; references to non-existent ids MUST be caught by Knowledge Validation
  (FR-024).
- **FR-016**: Chunks referenced by EvidenceReferences MUST remain immutable. Knowledge
  Representation MUST NOT modify, annotate, or replace any Chunk in the input ChunkSet.
  Knowledge Normalization similarly MUST NOT modify any EvidenceReference collection; it
  only normalizes the semantic content of Knowledge Units.

#### Knowledge Package

- **FR-017**: The Knowledge Package MUST be a self-contained, serializable, first-class
  entity for one document, exposing the following conceptual fields (per the KnowledgePackage
  Model): `knowledge_units` (ordered collection of Normalized Knowledge Units),
  `knowledge_relationships` (collection of typed Knowledge Relationships),
  `evidence_registry` (consolidated index of all EvidenceReferences in the package),
  `validation_report` (the KnowledgeValidationReport — always present), `metadata`
  (originating ChunkSet id, Document Model id, asset id, applied strategy identifiers,
  creation timestamp), and `statistics` (unit counts by type, relationship counts by type,
  EvidenceReference coverage percentage, and validation rule pass/fail counts). Every
  implementation of KnowledgePackage MUST expose all of these responsibilities.
- **FR-017a**: A published KnowledgePackage is **immutable**. Any modification to contained
  Knowledge Units or Knowledge Relationships MUST result in a new KnowledgePackage with a
  new identity rather than mutating the existing package. Downstream Representation
  Strategies consume the KnowledgePackage as a whole; they MUST NOT modify any field of the
  package they receive. This immutability guarantees deterministic processing,
  reproducibility, versioning, and auditability.
- **FR-018**: The Knowledge Package MUST be representation-agnostic: it MUST NOT assume,
  require, or pre-compute any specific downstream representation (Knowledge Graph, relational
  table, etc.) as part of its assembly. Vector representations (embedding-ready
  serializations) are downstream indexing artifacts and are not produced by this stage.
- **FR-019**: The Knowledge Package MUST be idempotent: re-running the same strategies on
  the same unchanged ChunkSet with the same configuration MUST produce a Knowledge Package
  with identical Knowledge Unit ids, types, content, relationships, and evidence references.

#### Knowledge Unit Extraction (Strategy Architecture)

- **FR-020**: Knowledge Unit Extraction MUST be strategy-based: all extraction logic MUST
  sit behind one stable, swappable interface; new extraction approaches MUST be addable by
  implementing this interface and registering the strategy, without modifying the pipeline's
  core dispatch logic or the Knowledge Unit model.
- **FR-021**: Named Entity Recognition (NER) MUST be treated as one optional, pluggable
  extraction strategy only. When NER is not configured, the pipeline MUST still function
  correctly using the default strategy; no NER-specific code path MUST exist in the pipeline
  core.
- **FR-022**: The default Knowledge Unit Extraction strategy MUST be deterministic and MUST
  NOT invoke LLM inference, embeddings, or any external network call to produce Knowledge
  Units. Non-deterministic or LLM-based strategies MUST be optional alternatives behind the
  same interface, never the default.

#### Knowledge Normalization

- **FR-023**: Knowledge Normalization MUST run as an explicit pipeline stage after Knowledge
  Unit Extraction and before Relationship Discovery. Its sole responsibility is to produce
  Normalized Knowledge Units by establishing canonical semantic identities, resolving aliases
  and synonyms, applying structural normalization, and detecting semantically duplicate
  units. Knowledge Normalization is a pure canonicalization stage with the following hard
  constraints: it MUST NOT introduce new semantic meaning into any Knowledge Unit; it MUST
  NOT infer new knowledge claims; it MUST NOT create Knowledge Relationships between units;
  it MUST NOT create new Knowledge Units other than canonical replacements for detected
  duplicates; it MUST NOT modify any EvidenceReference collection or any source evidence;
  it MUST NOT discard evidence from merged units.
- **FR-023a**: Knowledge Normalization MUST be strategy-based: all normalization logic MUST
  sit behind one stable, swappable interface (`KnowledgeNormalizer`). New normalization
  strategies MUST be addable by implementing this interface and registering the strategy,
  without modifying the pipeline's core dispatch logic, the Knowledge Unit model, or any
  downstream component.
- **FR-023b**: The default Knowledge Normalization strategy MUST be deterministic and
  rule-based. Non-deterministic or embedding-assisted normalization strategies (e.g.,
  embedding-based deduplication) MUST be optional alternatives behind the same interface,
  never the default.
- **FR-023c**: When Knowledge Normalization merges two semantically equivalent Knowledge
  Units into one canonical unit, the resulting unit's `evidence_references` collection MUST
  include the EvidenceReferences from all merged units — none may be discarded. Merged units
  MUST NOT remain in the Normalized Knowledge Unit set alongside their canonical replacement.

#### Relationship Discovery (Sub-Pipeline)

- **FR-023d**: Relationship Discovery MUST be implemented as an explicit two-stage
  sub-pipeline:
  1. **Relationship Candidate Discovery** — generates candidate relationships between
     Normalized Knowledge Units, producing `RelationshipCandidate` entities, each carrying:
     source and target Knowledge Unit ids, a relationship type, a collection of
     EvidenceReferences, and any strategy-specific scoring or rationale.
  2. **Relationship Validation** — filters or flags relationship candidates that violate
     quality constraints (dangling unit references, disallowed cycles per relationship type,
     insufficient evidence) before promoting surviving candidates to Knowledge Relationships.
  No other component in the pipeline MUST combine candidate generation and validation in
  one opaque step.
- **FR-023e**: Relationship Discovery MUST NOT modify Knowledge Units at any sub-stage. Its
  sole output is the collection of validated Knowledge Relationships; `RelationshipCandidate`
  entities are intermediate and are not included in the final Knowledge Package.
- **FR-023f**: The Relationship Discovery strategy (encompassing both sub-stages) MUST be
  swappable behind the `RelationshipDiscoverer` interface. New strategies MUST be addable
  without modifying the Knowledge Unit model, Knowledge Normalization, Knowledge Package
  Assembly, or Knowledge Validation.

#### Knowledge Validation

- **FR-024**: The Knowledge Representation stage MUST validate every assembled Knowledge
  Package against the following quality rules before producing output:
  (a) every Knowledge Unit has a non-empty collection of valid EvidenceReferences
      (FR-013–FR-015);
  (b) every Knowledge Relationship references only Knowledge Unit ids present in the package
      (FR-011);
  (c) every Knowledge Unit has a recognized semantic type (FR-005);
  (d) every EvidenceReference in every collection resolves all four traceability levels
      (FR-014).
  Violations MUST be either auto-corrected per a documented rule or surfaced as a named
  entry in the Knowledge Validation Report's `errors` (blocking) or `warnings`
  (non-blocking) — never silently passed through.
- **FR-025**: The stage MUST produce exactly one `KnowledgeValidationReport` per pipeline
  run, before the Knowledge Package is returned. The report MUST be an explicit, structured
  entity exposing the following conceptual responsibilities (per the KnowledgeValidationReport
  Model): overall `status` (`passed`, `passed_with_warnings`, or `failed`); `errors` (the
  named blocking rule violations, per FR-024); `warnings` (named non-blocking observations);
  `validation_results` (per-rule outcome records with implicated entity ids); `statistics`
  (counts of units/relationships checked, errors, warnings, and auto-corrections); and
  `metadata` (run identity, timestamp, rule set version). The report MUST be **immutable**
  once produced — it is an audit artifact; re-running the pipeline produces a new report.
- **FR-026**: The Knowledge Validation Report MUST be available for observability and
  debugging without requiring the Knowledge Representation pipeline to be re-run.

#### Representation Strategies (Optional Downstream)

- **FR-027**: The stage MUST support a pluggable `KnowledgeRepresentationStrategy` interface
  that accepts an immutable Knowledge Package and produces one specific downstream
  representation (Knowledge Graph, Property Graph, Semantic Network, Hypergraph, Relational,
  or others). Vector representations (embedding-ready serializations) are downstream indexing
  artifacts and are NOT a supported representation strategy for this stage.
- **FR-027a**: A Representation Strategy MUST be a pure read-only projection. It MUST
  consume the Knowledge Package; it MUST produce exactly one alternative representation
  format as output. It MUST NOT modify any Knowledge Unit, Knowledge Relationship,
  EvidenceReference, or Knowledge Package field. It MUST NOT create new Knowledge Units or
  Knowledge Relationships. It MUST NOT introduce new evidence or citations not present in
  the Knowledge Package. It MUST NOT persist, index, or embed Knowledge Package contents.
- **FR-028**: Representation Strategies MUST NOT produce side effects on the Knowledge
  Package or any of its contents. The Knowledge Package MUST be identical before and after
  any Representation Strategy is applied — this is verifiable by an equality check on the
  package before and after application.
- **FR-029**: New Representation Strategies MUST be addable without modifying the Knowledge
  Unit model, the Knowledge Relationship model, the pipeline core, or any other Representation
  Strategy.
- **FR-030**: The Knowledge Graph representation, when generated via a Representation
  Strategy, MUST be derived from Knowledge Units (nodes) and Knowledge Relationships (edges)
  — never the reverse; the Knowledge Graph MUST NOT be the primary or default output of the
  stage.

### Key Entities

- **KnowledgeUnit**: The primary semantic entity of this stage. A typed, independently
  meaningful, and **immutable** representation of one semantic fact, built from one or more
  chunks. Conceptual fields: `id` (stable deterministic identity), `type` (from the
  supported vocabulary), `semantic_content` (structured, not constrained to RDF triple or
  entity-span form), `participants` (named roles where applicable), `attributes`
  (qualifiers, units, scope, confidence), `evidence_references` (a non-empty **collection**
  of EvidenceReferences — never a single scalar), `relationships` (relationship ids
  populated after discovery; read-only on the unit), and `metadata` (extraction strategy,
  normalization status, timestamps). Once published into a Knowledge Package, a
  KnowledgeUnit is immutable; semantic changes produce a new unit with a new identity.
- **KnowledgeRelationship**: A typed, directed or undirected semantic relationship between
  two Knowledge Units. First-class entity, not an implicit graph edge. Conceptual fields
  (per the KnowledgeRelationship Model): `id` (stable deterministic identity), `relationship_type`
  (from the supported vocabulary), `source_unit` (id of the source Knowledge Unit),
  `target_unit` (id of the target Knowledge Unit), `evidence_references` (a non-empty
  **collection** of EvidenceReferences — never a single scalar), `attributes` (directionality,
  confidence qualifier if probabilistic, temporal scope), and `metadata` (producing strategy
  identifier, creation timestamp). Once published into a Knowledge Package, a
  KnowledgeRelationship is **immutable**; any modification produces a new relationship with a
  new identity.
- **EvidenceReference**: The complete traceability record linking a Knowledge Unit or
  Relationship to its sources. Carries: source Chunk id(s), source Structural Element id(s),
  Document Model identity, and asset/document identity. All four traceability levels are
  required; a partial EvidenceReference is invalid. EvidenceReferences always form a
  collection on a unit or relationship, never a single scalar.
- **KnowledgePackage**: The stage's terminal output for one document. A self-contained,
  serializable, validated first-class entity. Conceptual fields: `knowledge_units` (ordered
  collection of Normalized Knowledge Units), `knowledge_relationships` (collection of typed
  relationships), `evidence_registry` (consolidated index of all EvidenceReferences in the
  package), `validation_report` (the KnowledgeValidationReport), `metadata` (ChunkSet id,
  Document Model id, asset id, applied strategy identifiers, creation timestamp), and
  `statistics` (unit counts by type, relationship counts by type, evidence coverage,
  validation rule pass/fail counts). Representation-agnostic; Representation Strategies
  consume it as a whole without modifying it.
- **KnowledgeRepresentationStrategy**: A pluggable interface for generating one specific
  downstream representation format (Knowledge Graph, Property Graph, Semantic Network,
  Hypergraph, Relational, or others) from a Knowledge Package. A Representation Strategy is
  a **pure read-only projection**: it consumes an immutable Knowledge Package and produces
  an alternative representation artifact. It MUST NOT modify the Knowledge Package, any
  Knowledge Unit, any Knowledge Relationship, or any EvidenceReference. It MUST NOT create
  new Knowledge Units or Relationships. The Knowledge Package MUST be identical before and
  after strategy application.
- **KnowledgeValidationReport**: The formal structured outcome of Knowledge Validation and
  an immutable audit artifact. Conceptual fields (per the KnowledgeValidationReport Model):
  `status` (`passed`, `passed_with_warnings`, or `failed`), `errors` (named blocking rule
  violations, per FR-024), `warnings` (named non-blocking observations), `validation_results`
  (per-rule outcome records with implicated unit/relationship ids), `statistics` (units
  checked, relationships checked, error count, warning count, auto-correction count), and
  `metadata` (run identity, validation timestamp, rule set version). Produced exactly once
  per pipeline run before the Knowledge Package is returned; **immutable** once produced —
  re-running the pipeline produces a new report, not a mutation of this one.
- **KnowledgeUnitExtractor**: The swappable interface behind which all Knowledge Unit
  Extraction strategies sit. One extractor implementation = one pluggable strategy (e.g.,
  structural-pattern-based, NER-based, procedure-parser, math-expression-parser). The default
  is deterministic and structure-based. Produces raw Knowledge Units.
- **KnowledgeNormalizer**: The swappable interface behind which all Knowledge Normalization
  strategies sit. One normalizer implementation = one pluggable strategy (e.g., rule-based
  alias resolution, embedding-assisted deduplication). The default is deterministic and
  rule-based. Receives raw Knowledge Units and produces Normalized Knowledge Units without
  modifying any EvidenceReference or source evidence.
- **RelationshipDiscoverer**: The swappable interface behind which all Relationship Discovery
  strategies sit, encompassing both Relationship Candidate Discovery and Relationship
  Validation sub-stages. One implementation = one pluggable strategy. The default is
  deterministic. Never modifies Knowledge Units at any sub-stage.
- **RelationshipCandidate**: An intermediate entity produced by Relationship Candidate
  Discovery — a proposed semantic relationship between two Knowledge Unit ids, carrying a
  relationship type, a collection of EvidenceReferences, and any strategy-specific scoring
  or rationale. Consumed by Relationship Validation; not part of the final Knowledge Package.

### Non-Functional Requirements *(constitution-aligned)*

- **NFR-001**: The Knowledge Representation stage MUST respect Clean Architecture layering:
  Knowledge Unit and Relationship model definitions in domain/core; extraction and discovery
  strategy orchestration in application; any external integration (if ever added) in
  infrastructure; no domain-specific Python in core.
- **NFR-002**: Extraction and relationship discovery MUST be async/Celery-compatible for
  CPU-intensive workloads; no blocking operations in HTTP request handlers.
- **NFR-003**: All extractor, normalizer, relationship discoverer, and representation strategy
  implementations MUST be swappable via a factory/registry (Constitution Principle V);
  strategy selection MUST be configuration-driven per YAML pack precedence, never via ad-hoc
  conditional branching in callers.
- **NFR-004**: Downstream answer paths that consume Knowledge Packages MUST return source
  citations traceable to the originating chunks and documents via EvidenceReferences
  (Constitution VI.4).
- **NFR-005**: Public Knowledge Unit, Knowledge Relationship, EvidenceReference, and
  Knowledge Package classes MUST include type hints (Pydantic models), consistent with
  existing `core/document_intelligence/` conventions.
- **NFR-006**: Unit and integration tests MUST cover: Knowledge Unit type correctness per
  semantic form; evidence traceability integrity (all four chain levels, collection
  non-empty); Knowledge Unit immutability enforcement; Knowledge Relationship immutability
  enforcement; Knowledge Package immutability enforcement (equality check before/after
  Representation Strategy application); Knowledge Normalization correctness (alias
  resolution, deduplication with evidence preservation, MUST NOT infer new knowledge);
  Relationship Discovery sub-pipeline (candidate generation and validation separately
  testable); Knowledge Validation report completeness (all conceptual fields present);
  idempotent re-processing; strategy swappability (zero downstream contract change); and
  representation strategy read-only projection verification (package unmodified after
  application).
- **NFR-007**: Structured logging MUST record, at minimum, per-asset Knowledge Unit counts
  by type, Knowledge Relationship counts by type, validation rule pass/fail counts, and
  applied strategy identifiers, at existing Celery task logging boundaries.
- **NFR-008**: No secrets or credentials are introduced by this feature. If an optional
  extraction strategy requires credentials (e.g., an external NLP API), they MUST follow
  existing secret-management rules (Constitution IX).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On a fixture ChunkSet containing chunks of at least five distinct semantic
  forms (procedure, definition, measurement, table record, assertion), 100% of chunks
  produce at least one Knowledge Unit of the correct semantic type — with zero chunks
  silently dropped or collapsed into an incorrect type.
- **SC-002**: For every Knowledge Unit and every Knowledge Relationship in a fixture
  Knowledge Package, 100% have a non-empty `evidence_references` collection, and every
  reference in each collection resolves completely through all four traceability levels
  (Chunk → Structural Element → Document Model → original document), with zero broken or
  missing links.
- **SC-003**: For a fixed ChunkSet and extraction configuration, repeated runs of the
  Knowledge Representation pipeline produce identical Knowledge Package contents (Knowledge
  Unit ids, types, content, relationships, evidence references) 100% of the time.
- **SC-004**: Swapping the active Knowledge Unit Extraction strategy for a fixture project
  requires zero code changes outside the new strategy implementation and its registration —
  verified by a documented smoke test showing zero diffs under the pipeline's core dispatch
  logic, the Knowledge Package model, and any downstream consumer.
- **SC-005**: On a fixture containing intentionally malformed inputs (a Knowledge Unit with
  no EvidenceReference, a dangling Relationship reference, and an unrecognized type), 100%
  of violations are caught and reflected in the Knowledge Validation Report's `errors`
  or `warnings` with zero violations silently passing through to the Knowledge Package.
- **SC-006**: Applying two different Representation Strategies (e.g., Knowledge Graph and
  Relational) to the same Knowledge Package produces two different output formats; the
  Knowledge Package is identical before and after both applications, with zero modifications
  to Knowledge Units, Relationships, or Evidence References.
- **SC-007**: On a fixture ChunkSet, the Knowledge Representation stage produces a valid
  Knowledge Package with a complete Knowledge Validation Report without invoking any
  embedding call, vector similarity computation, graph database query, or retrieval engine
  call — confirmed by an integration test that runs the stage with no such infrastructure
  available.
- **SC-008**: End-to-end Knowledge Representation time for a representative fixture ChunkSet
  does not exceed an agreed latency budget versus the chunking stage's own processing time
  (exact ratio to be set during planning, measured against a recorded baseline).
- **SC-009**: On a fixture containing NER-compatible input, configuring the NER extraction
  strategy produces entity-type Knowledge Units. Switching back to the default strategy
  produces non-entity Knowledge Units. In both cases the Knowledge Package structure,
  Evidence Model (with non-empty `evidence_references` collections), Knowledge Normalization
  output, and Knowledge Validation Report shape are identical — confirming NER is one
  optional strategy, not a structural requirement.
- **SC-010**: On a fixture ChunkSet containing a concept expressed under two distinct
  surface forms across different chunks, the Knowledge Normalization stage (with the default
  deterministic strategy) produces exactly one canonical Knowledge Unit for that concept,
  whose `evidence_references` collection includes references to both source chunks, with zero
  evidence discarded.
- **SC-011**: On a fixture Knowledge Package, 100% of Knowledge Unit objects are confirmed
  immutable after publication: any attempt to modify `type`, `semantic_content`,
  `participants`, or `attributes` on a published unit either raises an error or produces a
  new distinct unit with a new identity — verified by an architecture/contract check that no
  pipeline component mutates an already-published KnowledgeUnit in-place.
- **SC-012**: On a fixture input, separating Relationship Candidate Discovery from
  Relationship Validation is confirmed by observing that the intermediate
  `RelationshipCandidate` collection contains at least one candidate that does not survive
  Relationship Validation (e.g., a dangling reference or a constraint violation), verifying
  that the two sub-stages operate independently and that only validated candidates enter the
  Knowledge Package.

## Assumptions

- `007-intelligent-chunking-engine` is implemented and produces validated ChunkSets with
  stable chunk identities, lineage, and parent/child/previous/next relationships. This stage
  depends on that output as its sole input.
- `006-document-intelligence-pipeline` Canonical Document Model (DocumentModel /
  StructuralElement) is accessible to this stage for EvidenceReference construction; this
  stage does not re-run document parsing.
- The default Knowledge Unit Extraction strategy is structure-based and deterministic, using
  the structural type and content of source Chunks to assign Knowledge Unit types — without
  requiring any LLM inference. LLM-based or embedding-based extraction strategies are
  reserved as explicitly configured, optional alternatives behind the same interface.
- The default Knowledge Normalization strategy is rule-based and deterministic (e.g., exact
  and near-exact string matching for alias detection). Embedding-assisted normalization is
  an optional alternative; it is never the default.
- Knowledge Unit, Knowledge Relationship, Knowledge Package, and Knowledge Validation Report
  immutability are logical constraints enforced by this specification. The implementation-
  phase choice of how to enforce immutability (e.g., frozen Pydantic models, copy-on-write,
  version identifiers) is a planning-phase decision; the constraint itself is not.
- Vector representations (embedding-ready serializations) are explicitly out of scope for
  this stage. They are downstream indexing artifacts produced by separate components that
  consume the Knowledge Package.
- NER-based extraction, if used, is treated as a library call (not a network call to an
  external service) in the default configuration; any external NLP service integration
  requires credentials managed per Constitution IX.
- The Knowledge Package is not the terminal persistence layer: downstream indexing,
  retrieval, reasoning, and answer generation stages will consume the Knowledge Package
  through their own adapters; this stage does not design or implement those adapters.
- "Domain-agnostic" means: no domain-name conditionals in core; domain-specific extraction
  behavior (e.g., recognizing pharmaceutical dosage measurements as a `measurement` type
  versus a generic assertion) is expressed via domain YAML pack configuration and the
  strategy's parameterization.
- The Knowledge Graph is NOT designed or generated by this spec — only the `KnowledgeRepresentationStrategy` interface and the concept of an optional Knowledge Graph
  artifact are specified here; the Knowledge Graph representation strategy implementation is
  a separate, future deliverable.
- This stage does not change chunking, retrieval, reranking, or answer generation logic.

## Out of Scope

- Embedding generation, vector indexing, retrieval, ranking, reranking, query planning, and
  answer generation — these are downstream consumers of the Knowledge Package, not part of
  this stage. Vector Representation is not a supported Representation Strategy for this stage.
- Implementing any specific Representation Strategy beyond specifying the interface (the
  Knowledge Graph strategy implementation, the Property Graph strategy, etc. are separate
  work items).
- Graph database integration, RDF serialization, SPARQL endpoints, or any graph storage
  implementation.
- Adding new raw format parsers or changing OCR providers/engines (unchanged from `006`).
- NER model training, NLP model fine-tuning, or any ML model development — NER is an
  optional pluggable strategy; the models themselves are not developed here.
- Designing the reasoning, planning, or answer generation stages that will consume Knowledge
  Packages — these are future specs.
- Any change to the ChunkSet output contract of `007-intelligent-chunking-engine`.
- Per-domain (pharmacy, legal, etc.) Knowledge Unit Extraction code in core — all
  domain-specific behavior is expressed via YAML pack strategy configuration.

## Dependencies

- `007-intelligent-chunking-engine` — **hard dependency**; the validated ChunkSet (including
  chunk identity, lineage, relationships, and provenance) is the sole input to this stage.
- `006-document-intelligence-pipeline` — **dependency**; the Canonical Document Model
  (DocumentModel / StructuralElement) is required for the EvidenceReference chain
  (Structural Element ids, Document Model identity).
- `002-field-registry` — field-pack precedence (generic < domain < project) that strategy
  selection and configuration builds on.
- `003-architecture-refactor` — `core/` / `services/` layering that hosts the new Knowledge
  Representation module.
- `005-answer-quality` — downstream beneficiary; structured, typed, evidence-traced Knowledge
  Units are expected to improve citation quality (AQ citation metrics) and retrieval
  precision; this stage is a prerequisite for that spec's knowledge-grounded answer targets.
- Future **Reasoning / Planning** stage (not yet specified) — this stage's Knowledge Package
  is scoped to serve as its canonical input.
- Future **Knowledge Graph Strategy** implementation — will consume KnowledgeRepresentationStrategy interface defined here.
